## 4. The central adversarial question -- has Model E actually changed anything?

**Ordinary-process mint exclusion.** Model D's defect (independently re-confirmed against the frozen S30B.1 defect reconstruction, itself reproduced verbatim from the live pre-repair source): the mint primitive was gated only by object-identity equality against a bare, unprotected module-level `object()` global, readable by any same-process code that imports the defining module. Model E's HPAC-PAWA-HELPER-REQ-145 relocates the mint primitive and its seal into a module that is, by contract, never imported by any agent-reachable code path -- the exclusion mechanism becomes literal absence from the ordinary process's address space (an OS-process-boundary fact), not a checkable-but-forgeable attribute inside a shared interpreter. This is a different class of guarantee. **VERIFIED AT THE CONTRACT LEVEL** -- its runtime realization cannot be exercised because the module does not exist yet; that is an expected limitation of a contract-only IV, not a defect.

**No broad isinstance-based legacy recognition.** HPAC-PAWA-HELPER-REQ-148/151 and PAWAH-INV-20 require recognition predicates to use exact-type or sealed-family checks, explicitly in both directions (a helper-scoped authority cannot satisfy legacy recognition, and a legacy authority cannot satisfy a helper-scoped predicate). This directly closes the predecessor IV's central finding ("same runtime class, indistinguishable to the store"). **VERIFIED AT THE CONTRACT LEVEL.**

**Three authority families kept mechanically separate.** Each family is a distinct type; each of the three facades mints only its own family; the store-recognition matrix denies every cross-family cell. This is a type-level separation, not a field-level one -- a structural improvement over Model D's shared-class-plus-descriptive-fields design. **VERIFIED.**
