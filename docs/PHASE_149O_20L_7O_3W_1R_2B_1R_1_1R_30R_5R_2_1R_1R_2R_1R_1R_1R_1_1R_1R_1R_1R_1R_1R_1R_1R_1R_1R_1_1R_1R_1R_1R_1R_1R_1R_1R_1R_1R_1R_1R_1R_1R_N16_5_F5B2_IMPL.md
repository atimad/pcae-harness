## Repair Architecture

**Contract status:** SUFFICIENT (carried forward from predecessor adjudication — `HPAC-PAWA-001` §32 already defines factory-consumer recognition as the actual importing/calling source module, a build-time/import-time fact, not a caller assertion).

**Mechanism selected:** removal of the caller-controlled early-return in the single shared primitive `_detect_caller_module` (`src/pcae/core/hpac_protected_admin_writer.py`). The `explicit` parameter (`_caller_module` keyword argument on all four factories) is retained for call-site/signature continuity but is unconditionally ignored (`del explicit`) — it can no longer influence the returned consumer identity under any circumstance. Real consumer identity is now, unconditionally, derived by walking the live call stack (`inspect.stack()`, `frame.f_globals["__name__"]`) to the actual calling module — the same mechanism the primitive already used as its *fallback* path pre-repair, now made the *only* path.

**Alternatives considered and rejected** (per predecessor's five-option menu):
- *Fixture-only-gated override* (retain `explicit` but route it only into `_TEST_FACTORY_CONSUMERS` never `AUTHORIZED_FACTORY_CONSUMERS`): rejected — still requires threading two distinct signals (asserted vs. real) through `_run_recognition_sequence`, and any test needing to simulate a genuinely *unauthorized* real caller would trivially already look "real" and authorized from its own vantage point, defeating the negative-test cases. More moving parts for no additional security margin over outright removal.
- *Process-local trusted consumer capability / new trust root*: rejected outright per §26/§37 of the phase order — no new trust root permitted, and unnecessary since the existing stack-provenance fallback already satisfies the supported threat model once made unconditional.
- *Private/internal-only factory rename*: rejected as insufficient alone per §46 of the phase order — a leading underscore is not a mechanical trust boundary.
- *Trusted wrapper/closure boundary*: rejected as unnecessary — the four factories already share one primitive; fixing that one primitive is the smallest compliant change and requires no new wrapper layer.

**Supported threat model (§5 of the phase order):** external installed Python callers, unrelated repository modules, ordinary PCAE agents/CLI/plugins/runtime modules, phase-local harnesses, and test modules using the supported factory API — none of these can obtain privileged authority merely by asserting an authorized consumer's name. Not claimed: defense against arbitrary hostile code already executing with unrestricted debugger/reflection/monkeypatch power inside the same trusted interpreter (no existing PCAE contract requires that stronger property here).

**Forged-module-name / `exec` attack (§44):** N/A — the repaired mechanism does not rely on any caller-suppliable global (it does not consult `_caller_module`/`explicit` at all); it reads `frame.f_globals["__name__"]` of the actual calling frame, which for a supported caller means their genuine top-level module identity as populated by Python's own import machinery, not a value a caller passes as a function argument. A caller could still construct a module object with `exec(code, {"__name__": "<authorized consumer>"})` and call the factory *from inside that manufactured frame* — but doing so does not let an *external* unauthorized module borrow another module's authority through the public keyword-argument surface, which was the actual finding (CALLER-SUPPLIED CONSUMER NAME AS A PARAMETER satisfying authorization). Manufacturing a whole forged execution frame to relabel one's own identity is a materially different, already-out-of-scope capability (equivalent to writing and running unrestricted arbitrary code under the target module's own name, i.e. the excluded "hostile code already executing with unrestricted power" case), not a supported-caller attack against the public API surface addressed here.

**Import-alias/wrapper test (§45):** N/A for the same reason — no caller-suppliable identity string exists post-repair for a wrapper to launder.
