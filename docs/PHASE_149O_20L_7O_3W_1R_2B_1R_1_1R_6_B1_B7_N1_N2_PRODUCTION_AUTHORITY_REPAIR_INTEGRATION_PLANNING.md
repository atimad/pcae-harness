## 2. Production defect re-derivation (from current source, not historical prose)

All four defects were independently re-derived directly against current
`src/pcae/core/*.py`, not trusted from summary prose. Citations below are

### 2.1 B1 — trusted approval projection seal is transferable/copyable

**Current mechanism:** `runtime_authority.ValidatedAuthorityProjection`
carries a `_validator_seal` field (`runtime_authority.py:774`), checked by
`is_trusted_validated_authority_projection` (`:812`) via identity
comparison against a single module-level `object()` singleton
`_VALIDATED_AUTHORITY_SEAL` (`:774`). The seal is:

- **Identity-only, not content-bound** — nothing ties the seal to the
  specific fields it was issued for.
- **Not persisted** as a sealed/canonical artifact; downstream code trusts
  the field's identity alone.
- **Copyable**: `dataclasses.replace()` preserves the `compare=False` seal
  field verbatim while every other field (`approval_id`, `record_digest`,
  `subject_scope_binding_digest`) can be overwritten arbitrarily. No
  canonical-store re-resolution occurs at validation time.

**Re-derived defect:** the seal answers "was this object constructed by
the trusted builder function at some point," not "are these specific
field values currently authorized." Those two questions were conflated.
This is the same root cause the original `.1R.1` independent verification
found OPEN (`docs/PHASE_149O_20L_7O_3W_1R_1_INDEPENDENT_VERIFICATION_RUNTIME_INVOCATION_AUTHORITY_PB_DISPATCH_FOUNDATION_BLOCKING_REPAIR.md`
§6 Matrix A: "object seals ... copied projection seal ... both obtain
simulated ALLOW" — **OPEN**), and it remains bit-for-bit unrepaired in the
current tree — confirmed independently this phase, not assumed from that
report.

`AuthenticatedHumanPrincipal`'s verifier-owned identity-registry pattern
(§3 below) is structurally the right kind of mechanism to replace this —
but naively substituting one identity-only seal for another
(`AuthenticatedHumanPrincipal` treated as *itself* the trusted approval
seal) would just recreate B1 one layer up. See §7 (repair principle).

### 2.2 B7 — dispatch identity is reproducible from public data, registry unrechecked

**Current mechanism:** `runtime_dispatch_permission.RuntimeDispatchIdentity`
(`:231`) is generated by `_identity_registration_digest` (`:249`), a plain
unkeyed digest over `(invocation_id, attempt_id, idempotency_key)` — all
public, caller-visible facts. `build_runtime_dispatch_permission_broker_request`
(`:451`) checks the identity seal and recomputes the digest (`:473-474`),
but **never re-reads** the durable `RuntimeDispatchIdentityTracker` registry
(`:290`, backed by `.pcae/runtime-dispatch-identities/v1/**`) at request-build
time. State can change between identity generation and dispatch with no
revalidation against durable registry state.

**Re-derived defect:** RDGO-001 v3.0 assigns the "freshly resolves the
canonical approval ... not cached authority" responsibility to **Gate 5**
(`docs/contracts/RUNTIME_DISPATCH_GATE_ORDERING_CONTRACT.md` §6, line
148-150; §"Validation is not cached authority", line 460) — but **Gate 5
does not exist anywhere in source**; it is referenced only in
`hpac_verifier.py` docstrings as a future caller. There is currently no
component that owns dispatch-time revalidation at all, so verifier-result
(or registry-state) reuse across the generation→dispatch window is
undefined, not merely unsafe.

### 2.3 N1 — approval objects can bypass canonical-store provenance

**Current mechanism:** `RuntimeInvocationApprovalStore.load()`
(`runtime_invocation_approval_store.py:53,173`) returns a bare
`RuntimeInvocationApproval` with no provenance marker distinguishing
store-issued from caller-constructed instances.
`runtime_authority.validate_approval` (`:820`) accepts any such object
directly: it checks `approval.provenance.approver_id` shape (`:858-860`)
but performs **no canonical re-resolution / lookup-by-ID** against the
store. `create_runtime_invocation_approval` (`:387`) is a public callable —
nothing prevents hand-constructing `RuntimeInvocationApproval` /
`ApprovalProvenance` directly and passing the result to `validate_approval`.

**Re-derived defect:** "valid-shaped approval object" and "approval this
process actually canonically issued and can still resolve by ID" are
different claims, and only the former is currently checked.

### 2.4 N2 — caller can manufacture human-looking provenance

**Current mechanism:** `ApprovalProvenance.approver_id` and
`.identity_evidence_kind` (`runtime_authority.py:291-292`) are ordinary
caller-supplied strings, validated only for enum membership
(`_IDENTITY_EVIDENCE_KINDS`, `:412`) and inequality with
`producer_component` (`validate_approval`, `:860`) — no independent
authentication of the string's referent. `create_runtime_invocation_approval`
(`:394-395`) accepts both as plain parameters.

**Re-derived defect:** "a string that looks like a human identifier and
isn't the producer's own identifier" is currently accepted as human
provenance. Nothing binds `approver_id` to any authenticated principal.

**Contract-status correction (see §11, Contradiction 1):** the `.1R.2`
sub-phase of this same family
(`docs/PHASE_149O_20L_7O_3W_1R_2B_1R_1_1R_2_HUMAN_PRINCIPAL_AUTHENTICATION_PROTECTED_APPROVAL_PRESENTATION_PROOF_LIFECYCLE_IMPLEMENTATION_PLANNING.md`)
explicitly **STOPPED** N2 repair because RIHAC-001 v1.0 forbade every
existing PCAE mechanism from supplying authenticated-human evidence, and
concluded new authentication architecture was required. The `.1R.3`
through `.1R.5.2.1` chain then built exactly that architecture (HPAC-001
v2.0, `hpac_verifier.py`) under contract *evolution* (RIHAC-001 v2.0), not
under the old frozen text. N2 is therefore correctly **open-for-repair
now** — but this transition was never previously stated as an explicit
"N2-STOP-lifted" decision anywhere in the phase docs. This document states
it explicitly.

## 5. Repair principle — how the HPAC foundation may (and may not) be consumed

The core risk this whole phase family exists to prevent is collapsing:

```text
confirmed != authenticated != approved != permitted != capable != executed
```

and specifically:

```text
AuthenticatedHumanPrincipal != approval != RIHAC projection != PB permission
!= runtime capability != execution

deterministic NON-REAL verification != real human authentication
```

**The repair must not create a new B1-style transferable seal using
`AuthenticatedHumanPrincipal`.** Concretely: no downstream consumer may
treat "I was handed an `AuthenticatedHumanPrincipal` object" as sufficient
by itself. Every consumption point must call
`is_verifier_authenticated_principal(...)` (registry re-check, not
type/shape check) **and** re-resolve the surrounding canonical state
(approval record, dispatch identity, invocation binding) from its
authoritative store at the point of use, not accept a caller-passed
object on faith. This is the same discipline the verifier itself already
applies internally; the repair's job is to extend it outward one layer,
not to introduce a new trusted-by-shape object at the boundary.

### 5.1 B1 repair

Replace `_validator_seal`'s identity-only trust with:
(a) principal-derived approver identity (§5.4, N2) instead of a bare
approver-id string, **and**
(b) a structural, content-bound binding — the "seal" becomes a value
recomputed from the record's own current canonical fields plus invocation
binding, not a token that survives `dataclasses.replace()` for free. A
copied/mutated projection must fail re-validation because the recomputed
binding no longer matches the mutated fields, not because a `compare=False`
flag happens to differ.

### 5.2 B7 repair

`build_runtime_dispatch_permission_broker_request` must re-read the durable
`RuntimeDispatchIdentityTracker` registry at request-build time and
fail-closed on any mismatch between the presented identity and current
registry state (revalidation, not cached trust). Until a real Gate 5
coordinator exists, this revalidation call is added directly inside
`runtime_dispatch_permission.py` at the existing request-build choke
point — it does not require inventing Gate 5 first (§8).

### 5.3 N1 repair

`validate_approval` must resolve the approval by ID against
`RuntimeInvocationApprovalStore` (canonical lookup) rather than trusting a
caller-passed object's field values. A caller-constructed
`RuntimeInvocationApproval` that does not resolve to an identical
store-held record must be rejected, regardless of internal shape validity.

### 5.4 N2 repair

`approver_id`'s trust basis changes from "any enum-valid string" to
"derived from an `is_verifier_authenticated_principal`-passing
`AuthenticatedHumanPrincipal`, at the moment of approval creation." The
verifier-issued principal supplies the human-identity fact;
`create_runtime_invocation_approval` stops accepting a free-form
`approver_id` string as an authority-bearing input and instead accepts
(and records provenance of) the principal object, deriving `approver_id`
from it. Caller-supplied strings remain permitted only for
non-authority-bearing metadata (e.g. free-text notes), never for the
provenance-authority field itself.

## 6. Authenticated principal vs. approval — explicit staging

```text
authenticated principal (HPAC verifier, NON-REAL today)
        ↓
protected human approval act   [NOT built by this repair — see §7]
        ↓
canonical approval authority   (N1/N2 repair: store-resolved, principal-derived)
        ↓
RIHAC authority projection     (B1 repair: structural, content-bound — not yet the
                                 full typed PBRD-v2 projection, see §7)
```

Successful `verify_human_authentication` (NON-REAL) proves only
*authentication* semantics. It must never, by itself, fabricate the
"protected human approval act" stage. Repairing B1/B7/N1/N2 replaces the
*provenance and revalidation plumbing* around approval and dispatch
identity; it does not, and must not, cause authentication success to
imply approval. The approval act itself (today: a deterministic
test-fixture presentation, per HPAC-001 v2.0) remains a separate,
explicit step that the repair wires to but does not eliminate.

## 7. Staging decision (Option A, verified)

Section 13's three options were evaluated against the current source
state:

- **Option A** — repair production authority plumbing structurally, keep
  all real authority outcomes fail-closed because only NON-REAL
  authentication exists.
- **Option B** — repair only canonical provenance/consumption plumbing,
  defer positive authority projection until real FIDO2/UI exist.
- **Option C** — split into two bounded phases.

**Decision: Option A**, implemented as one production repair phase (§10),
with a single explicit hard-rejection point (§8) that keeps positive
production authority unreachable until real FIDO2 exists — not two
phases split along the real/NON-REAL line, because B1/B7/N1/N2's actual
defects (copyable seal, stale registry, non-canonical approval, caller-
manufactured identity) are **all provenance/revalidation defects**, not
"premature positive authority" defects. They can be fully closed while
mechanism assurance stays permanently NON-REAL today, by making the hard-
rejection point assurance-gated rather than omitting the plumbing
entirely. Option B would leave the plumbing half-built for no safety
benefit Option A doesn't already provide via the hard-rejection point.

This also answers §24/§25 directly: **yes**, B1/B7/N1/N2 production
plumbing can be safely implemented before real FIDO2 and before the real
protected UI exist, *provided* the hard-rejection point in §8 is in place
before any of the plumbing is wired live. Verified by construction: every
repaired consumption point (§5.1–§5.4) is designed to route through
`is_verifier_authenticated_principal` plus canonical-store resolution;
none of them independently manufacture authority from unauthenticated
data.

## 8. Deterministic NON-REAL hard-rejection point

**Owner: the canonical-approval-authority construction step inside
`runtime_authority.py`** (the N1/N2-repaired `create_runtime_invocation_approval`
/ `validate_approval` pair) — **not** Gate 5, because Gate 5 does not exist
in source and this repair does not create it (§7, §10). This is a
deliberate, explicit choice among the candidates listed in the governing
prompt (RIHAC projection construction; approval canonicalization; Gate 5;
Gate 9; runtime-authority adapter): **approval canonicalization** is
selected as the interim choke point because it is the first place, in the
current call graph, where a principal's authentication result is
converted into anything authority-bearing.

Rule: canonical approval authority creation **must** check
`principal.mechanism_assurance` (a field this repair adds to whatever
provenance record accompanies the principal — not a new field on
`AuthenticatedHumanPrincipal` itself, which stays verifier-internal) and
reject with a fail-closed error if assurance is not `REAL`. Since
`verify_human_authentication` only ever produces NON-REAL principals
today, this rejection is unconditionally active in production until real
FIDO2 exists — i.e., the plumbing is fully wired, but no code path can
currently produce a passing canonical approval outside test fixtures that
explicitly assert NON-REAL/test-only intent through a separate,
non-production-reachable fixture constructor (§9).

When a real Gate 5 coordinator is eventually built (a later, unscheduled
chapter — see §10.3), this same check moves to become one of Gate 5's
responsibilities as RDGO-001 §6 anticipates; it is not removed, only
relocated.

## 9. Test-only approval fixture path vs. real production eligibility

Two distinct construction paths must exist and remain distinguishable
at the type/module level, not just by convention:

- **Test-only fixture path**: explicitly named (e.g. a
  `construct_test_only_deterministic_approval(...)` helper, importable
  only from test code by repository policy, not from any production
  module), which is allowed to accept a NON-REAL principal because it
  never routes through the production hard-rejection point in §8 — it
  bypasses canonical persistence entirely and produces an object usable
  only by tests exercising the plumbing shape.
- **Real production path**: `create_runtime_invocation_approval`, gated by
  §8, unconditionally fail-closed today.

The plan requires the next implementation phase to make this boundary
enforceable by an automated check (e.g. an AST-based test forbidding
production modules from importing the fixture constructor), following the
same precedent `.1R.5.2.1` already used to verify zero production
consumers of `hpac_verifier.py`.

## 10. Gate architecture (forward planning, not implemented this phase)

### 10.1 Gate 5 (future)

RDGO-001 v3.0 §6 responsibilities, restated as an explicit checklist for
the later Gate 5 coordinator: revalidate authenticated-principal
provenance (registry re-check, not object trust), principal currentness,
credential currentness, proof freshness, proof lifecycle state,
presentation evidence, approval canonicality (store re-resolution),
invocation identity match, RIHAC projection shape, assurance/mechanism
eligibility (the §8 check, relocated here), revocation, expiry. Earlier
verifier success is never treated as permanently valid — Gate 5 always
re-resolves.

### 10.2 Gate 9 (future)

An **inert Gate-9 model/store already exists**:
`src/pcae/core/runtime_invocation_authority_consumption.py` (214 lines).
Its own docstring (lines 1-13) states it "Implements ONLY the record
schema (HPAC-REQ-098) and a create-only, atomic, duplicate-detecting store
(HPAC-REQ-099/100). There is NO RDGO-001 gate wiring here, no gate-9
caller, and no consumption of any real approval ... reachable only by test
code constructing its own inert records." Built during `.1R.3` (Layer
1-2 foundation). The future Gate 9 coordinator must define: exact
preconditions (Gate 5 passed), serialization boundary, lock/transaction
ownership, in-boundary state revalidation, proof + approval consumption
together (atomic), replay behavior (reject), process-crash-before-commit
behavior (authority remains unconsumed, safely retryable), process-crash-
after-commit behavior (retry reports "already consumed," per RDGO-001
duplicate `attempt_id` → "Hard collision; fail closed," line 502),
partial-write prevention (inherits from the store's existing atomic
create-only guarantee).

### 10.3 Gate 10 (unchanged boundary)

Remains the first external execution effect (RDGO-001 §11). Nothing in
this repair, nor its forward Gate 5/9 planning, moves any side effect
earlier. No production dispatch work occurs in `.1R.6` or its successor.

### 10.4 Why Gate 5/9 coordinator wiring is deferred, not bundled

B1/B7/N1/N2 are defects in the **pre-gate production modules**
(`runtime_authority.py`, `runtime_dispatch_permission.py`,
`runtime_invocation_approval_store.py`) that exist and are called
directly today, independent of whether an RDGO gate coordinator exists.
Building an actual Gate 5/9 coordinator is a materially larger
architectural undertaking (a new orchestration component, not a repair of
an existing one) with a different trust/atomicity boundary. Bundling it
into the B1/B7/N1/N2 repair would violate "do not bundle unrelated trust
boundaries" (§35 of the governing prompt). It is therefore named as a
distinct, later, **unscheduled** chapter — no phase ID is invented for it
(consistent with this project's no-invent-an-ID discipline) — while its
responsibilities are still planned here (§10.1–§10.3) so the repair
implementation doesn't foreclose it.

## 15. Restart and freshness/TOCTOU planning

`_AUTHENTIC_PRINCIPAL_REGISTRY` is a plain in-process `set()`, keyed by
Python object identity (`__hash__` = `id(self)`, `__eq__` = `self is
other`) — confirmed structurally, not merely asserted: a
serialized/reconstructed principal cannot regain membership because
membership is identity-based, not value-based, and nothing persists the
registry to disk. Therefore: **re-authentication is mandatory after
process restart** — no production consumer may treat a principal as valid
across a restart boundary, and the next implementation phase's tests must
include an explicit "simulated restart (fresh registry) rejects
previously-authenticated principal" case (case 7 above).

Between authentication, approval, and (eventually) Gate 5/Gate 9, state
can change. Until Gate 5 exists, **the approval-canonicalization step
(§8's owner) is the sole revalidation owner** for: principal registry
membership (re-checked at approval-creation time, not cached from an
earlier check), approval canonical-store resolution (§5.3), and dispatch
identity registry state (§5.2, at dispatch-request-build time — a
separate call site from approval creation, revalidated independently).
No stale authority is designed to survive into the (future) Gate 9
boundary, because nothing is currently allowed to reach Gate 9 at all
(§10.4) — this is deferred by construction, not left open.

## 16. Same-user-agent threat model (unchanged)

The repair continues to assume an autonomous coding agent may run under
the same OS account as the human. None of UID, username, process
ownership, stdin/stdout, Git identity, PCAE session identity, or producer
identity are trusted anywhere in the repaired plumbing. Only the verified
HPAC provenance chain (`is_verifier_authenticated_principal` + registry
re-check) establishes human authentication, exactly as today.

## 17. Implementation packaging decision

**One implementation phase** for B1/B7/N1/N2 together (not split further),
because:

- All four defects live in the same two production modules
  (`runtime_authority.py`, `runtime_dispatch_permission.py`) plus one
  already-existing consumed store; they share one trust boundary
  (production approval/dispatch authority), not several unrelated ones.
- B1 and N2's repairs are not independently meaningful — a content-bound
  seal (B1) built on a still-caller-manufactured approver identity (N2)
  is not actually repaired; the two must land together to avoid an
  intermediate state that is neither the old nor the new trust model.
- Splitting further than "one phase" would produce intermediate states
  where, e.g., N1's canonical-store enforcement is live but B1's seal
  isn't, which does not correspond to any coherent authority boundary and
  provides no independent testability benefit.

Gate 5/Gate 9 coordinator wiring is **not** part of this implementation
phase (§10.4) — it is a separate, later, unscheduled chapter.
