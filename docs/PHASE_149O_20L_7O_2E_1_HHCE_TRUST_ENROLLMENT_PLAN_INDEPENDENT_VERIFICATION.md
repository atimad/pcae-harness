## 14. Findings

**BLOCKING:** None found.

**NON-BLOCKING:**

- **NBF-149O.20L.7O.2E.1-1 (public_key field-format mischaracterization).** HHCE-REQ-002 (§5 of HHCE-001) describes `HardwareCredentialRecord.public_key` as "DER SubjectPublicKeyInfo" — this phrase is copied verbatim from a comment in `hatp_hardware_credentials.py`'s dataclass definition (`# DER SubjectPublicKeyInfo`, line 97), which is itself a documentation comment, not enforced by any validation code (`_parse_credential` only checks the field is valid hex, never its decoded structure). Direct read of `Fido2HardwareProvider.verify()` (`hatp_fido2_provider.py:389`) shows the field is actually consumed as `CoseKey.parse(cbor.decode(record.public_key))` — i.e., CBOR-encoded COSE_Key bytes (RFC 9052), not DER SubjectPublicKeyInfo. This is independently confirmed by the existing, already-passing test harness: `tests/test_phase_149o_2_hatp_hardware_provider_implementation.py::_cose_public_key_bytes` builds fixture records via `fido2_cbor.encode(dict(cose_key))`, the identical CBOR/COSE format `verify()` expects, never DER. **Classification rationale (Non-Blocking, not Blocking):** the mismatch fails closed, not open — a DER-encoded value would cause `CoseKey.parse` to raise inside `verify()`'s broad `except Exception`, yielding `signature_valid=False` (safe, functionally-broken, never a security hole). It also does not threaten Surface A's actual implementability: the companion implementation plan's own §6 already independently describes the correct format ("extract... the COSE public key from the resulting AttestedCredentialData"), so an implementer following the full contract+plan bundle is not misled in practice — only a hypothetical implementer reading HHCE-001 §5 in total isolation from the plan and from `hatp_fido2_provider.py` itself could be misled, and HHCE-001 itself instructs reading primary source first (§10 of its own architecture-basis header). **Recommended disposition:** HHCE-001 §5 (HHCE-REQ-002) should be corrected from "DER SubjectPublicKeyInfo" to "CBOR-encoded COSE_Key (RFC 9052), matching `Fido2HardwareProvider.verify()`'s existing, unmodified parsing" at or before Surface A implementation (149O.20L.7O.2F) — an editorial contract-text correction, not a dedicated repair phase, per governing-prompt §42's "avoid creating repair phases for editorial issues" instruction. This finding does not block 149O.20L.7O.2F from proceeding; it is a fix-in-passing item for that phase's own HHCE-001 companion-file consumption, or, if preferred, a same-scope-fits touch-up here (declined this phase — no Blocking contradiction was proven, so no contract edit was made here, preserving the narrow verification-only scope this phase's own no-go boundary requires).
