## 2. Root finding (carried forward, independently re-confirmed)

`_detect_caller_module(explicit)` (`src/pcae/core/hpac_protected_admin_writer.py:495-504`) returns any caller-supplied `explicit` value **verbatim**, before ever consulting the real call stack:

```python
def _detect_caller_module(explicit: Optional[str]) -> str:
    if explicit is not None:
        return explicit
    ...  # stack inspection fallback, only reached when explicit is None
```

Any caller of a factory that exposes `_caller_module` as a public keyword argument can assert the name of an authorized consumer and be trusted as that consumer, with no runtime verification that it *is* that consumer.

CONSUMER NAME != CONSUMER AUTHENTICITY. CALLER-SUPPLIED MODULE STRING != AUTHORITY. STATIC SOURCE-SCANNING GUARD != RUNTIME AUTHORIZATION BOUNDARY.

## 3. Exhaustive `_detect_caller_module` / `_caller_module` inventory

Repository-wide search (`grep -rln "_detect_caller_module\|_caller_module" src/`) found exactly **two** source files:

- `src/pcae/core/hpac_protected_admin_writer.py` — defines `_detect_caller_module` and all four privileged factories that call it.
- `src/pcae/core/hpac_certification_coordinator.py` — the **sole legitimate production forwarder**: `HpacCertificationCoordinator._mint` / `_obtain_read_authority` forward `self._seams.caller_module` to `certification_writer` / `recognized_certification_read_authority`. `_Seams.caller_module` defaults to `None`; real production construction (`HpacCertificationCoordinator()` with no seam kwargs) never sets it (test_03 below), so real production flow always falls through to genuine stack inspection, which correctly resolves `pcae.core.hpac_certification_coordinator` as the caller. **The coordinator itself is not the vulnerability** — the vulnerability is that the four factories it wraps are also independently, directly callable (they are public, non-underscore-prefixed module-level functions) by any other in-process code, which can supply the override directly.

No production consumer, factory, or override site exists outside these two files. The reported three-factory blast radius understated the true scope by one: **four** factories share the primitive, not three (see §4).

## 10. Threat model precision (§4, §41 of the prompt)

In scope (supported callers an unauthorized actor could realistically be, or become, without needing a second in-scope vulnerability): an ordinary PCAE agent/CLI code path, an unrelated `src/pcae` module, a future plugin, an external script against an installed wheel, or test code — anything able to call a public Python function in-process. This phase's diagnostic suite exercises exactly this class (its own module is outside every consumer allowlist).

Out of scope / not claimed: this finding does **not** assert isolation against arbitrary, already-unrestricted hostile Python executing in the same interpreter with reflection/monkeypatch powers (class D/E in the prompt's taxonomy) — PCAE's threat model does not claim that isolation elsewhere, and nothing here should be read as promising it. The defect is that a **normal, unprivileged public API call** — no reflection, no monkeypatching, no private-attribute access — suffices.

**Selected security property (§28, §69):**

> A privileged production factory's consumer-authorization check MUST be evaluated against the actual calling module — a mechanically trusted, build/import-time or equivalently-trustworthy runtime fact — never against a caller-supplied descriptive string. An unauthorized supported caller MUST NOT obtain privileged factory authority merely by supplying the name of an authorized consumer as an argument. This property does not require, and this phase does not claim, protection against arbitrary hostile Python already executing unrestricted inside the same trusted interpreter.

## 11. Candidate repair architectures compared (§29-33)

| Candidate | Assessment |
|---|---|
| **A. Remove the caller override from the production path; infer the actual caller only from trusted stack/module inspection** | Reuses the *existing* fallback branch of `_detect_caller_module` (already present, already used whenever `explicit is None`) — no new trust root. Weakness: stack inspection is spoofable by a sufficiently adversarial same-interpreter caller (frame manipulation), but that is class D/E, already out of PCAE's stated threat model (§10) and not weaker than other recognition-sequence conjuncts already accepted (e.g. topology probes). Preserves testability for legitimate test consumers via the existing `_TEST_FACTORY_CONSUMERS` / `_CERTIFICATION_TEST_CONSUMERS` allowlists, which are matched against the *real* resolved module name of the test file, not an assertable string — this is exactly how `production_writer`'s own existing tests already work (§ "positive path" analysis, `AUTHORIZED_FACTORY_CONSUMERS` slice-1 tests use no `caller=` override at all). |
| **B. Retain the override, gate it behind a fixture-only authority unavailable in production** | Requires a second mechanism (an unforgeable "is this a test process" fact) that PCAE does not appear to already have as a reusable primitive for this purpose; risks becoming a second, novel trust root (§35 forbids this without strong justification). |
| **C. Process-local trusted consumer capability (non-bearer, minted at construction)** | Stronger in principle, but nothing calls these four factories through an existing capability-minting boundary today — introducing one is a larger architectural change than candidate A and does not obviously reuse an existing PCAE root (§31 concerns apply). |
| **D. Private/internal-only factories reachable solely through the coordinator wrapper** | Would remove the public keyword surface but doesn't itself establish *authenticity* — Python has no private-function enforcement; the same override problem re-appears one layer down at the wrapper unless the wrapper itself uses (A). Also a larger surface-area change (touches every legitimate caller of these functions, including the slice-1 admin script and the presentation-admin script) than is warranted for a consumer-identity defect. |
| **E. Trusted wrapper/closure boundary** | Same conclusion as D — reduces to "use A, but hide it," which is (A) plus unnecessary indirection. |

**No candidate requires a second trust root** (§35). Candidate **A** is the smallest change consistent with §32's own existing normative definition ("the importing / calling source module") and reuses machinery (`_detect_caller_module`'s existing stack-inspection fallback, the existing `_TEST_FACTORY_CONSUMERS`-family allowlists) that is already present and already governs the "no explicit override" path for every one of these four factories today. This phase does **not** select or freeze candidate A as final — that determination belongs to the successor implementation phase — but records it as the load-bearing evidence-supported direction (§30 explicitly forbids assuming stack inspection is automatically correct; the case for it here rests on §32's own text plus reuse of already-present testability machinery, not on convenience).
