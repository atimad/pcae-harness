## The repaired trust primitive

The N16-5-F-5-B2-IV predecessor proved that N16-5-F-5-B2-IMPL's repair
(walking `inspect.stack()` and trusting `frame.f_globals.get("__name__")`)
was itself forgeable: `__name__` is an ordinary key on a caller-constructed
globals dict, settable via `exec(code, {"__name__": "<authorized name>"})`
with no import-machinery registration required.

This phase's repair (`_verified_production_caller_name`) replaces that
single dict-key trust with a two-part, trust-on-first-use provenance check,
required only for the four factories' enumerated production-consumer names
(ordinary/test-consumer candidate names are handled exactly as before):

1. **Import provenance.** The candidate's `sys.modules[name]` must carry a
   genuine `__spec__.loader` that is an `importlib.machinery.SourceFileLoader`
   whose resolved `origin` matches the exact on-disk path the installed
   `pcae` package's own layout requires for that dotted name — derived
   solely from the already-imported `pcae` package's own `__file__`, never
   from `sys.path`, `cwd`, or anything caller-supplied. This defeats
   `sys.modules` poisoning with a hand-built module/spec.
2. **Code-object identity.** The calling frame's `f_code` must be
   object-identical to one of a snapshot of the module's own pre-existing
   function/method code objects, captured once at first-verified-use and
   pinned process-locally for the life of the process (kept alive against
   CPython `id()` reuse). This defeats `exec(forged_code, real_module.__dict__)`
   — a real module's `__dict__` is itself an ordinary, caller-referenceable
   object, so provenance-check (1) alone is insufficient; a forged call
   executing fresh, non-module code against that real dict must still be
   rejected, and the code-object pin is what does that.

A forged claim to an enumerated production-consumer name is rejected
outright — never re-attributed to an outer stack frame — via a guaranteed
non-matching `"<unverified-caller>"` sentinel, so the existing
`unauthorized_factory_consumer` (§56/§33 step 9) path fails it closed
exactly as it already fails any other unrecognized name.

**Disclosed residual limitation (trust-on-first-use):** the code-object
snapshot for a given consumer name is captured at whatever the first
verified call happens to be. No path was found by which an attacker could
inject a forged first sighting (the first-sighting check itself still
requires the candidate frame's code to already exist in the module's real,
freshly-collected `vars()`, which requires the module already be real), but
this is disclosed as a class of TOCTOU risk inherent to any
trust-on-first-use design in a fully mutable runtime, meriting explicit
adversarial attention in the required successor IV.
