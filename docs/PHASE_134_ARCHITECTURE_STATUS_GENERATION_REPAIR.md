# Phase 134E.8 — Architecture Status Generation Repair

## 1. Executive Summary

Recent canonical PCAE reports displayed a persistent, highly visible
defect: the auto-generated "PCAE Architecture Status" block claimed
`Planned: 132F — Repository Intelligence Service` despite Track 132
being independently verified complete, Track 133 substantially
complete, and Track 134 many phases into active execution — while the
block itself asserted *"Generated automatically from canonical project
state. Never manually maintained."* This phase traced the generation
path from source, established the exact root causes (three compounding
defects, not one), repaired them, established an explicit authority
model and semantic-freshness contract, added a validation API and a
read-only inspection command, and confirmed against the real repository
that the defect is gone. No Canonical Engineering Evidence, Evidence
Extraction, Phase Report View, Operator Report View, Rendering
Architecture, Delivery Pipeline, or Delivery Receipt subsystem was
activated. No execution capability was introduced. 134E.8V (independent
verification) has not begun.

## 2. Investigation and Stale-Output Evidence

The Architecture Status block is generated by
`pcae.core.phase_reports.build_architecture_status()` and rendered by
`PhaseReport.render_markdown()`. Running it against the real repository
before any change confirmed the reported defect exactly:

```
"planned": ["132F — Repository Intelligence Service"],
"in_progress": [],
"completed_phase_ids": [... capped at the 110-113 series only ...]
```

Three independent, compounding defects were found by direct source and
state inspection (never assumed from the incident description alone):

1. **Stale "planned" recommendation.** The regex matching the current
   phase's own recommendation only recognized the retired wording
   `"Recommended next repo phase:"`. Current phase reports write
   `"Recommended next phase:"` (no `"repo"`). Because the current
   section's own sentence never matched, generation fell through to a
   whole-file fallback search for the *old* wording and returned the
   **first** match — and because `PROJECT_STATUS.md` is ordered
   newest-first, the first occurrence of the old wording was many
   phases in the past, in the historical `## Phase 132F Complete
   (historical — full text)` section. This is the direct, sole cause of
   `"Planned: 132F"`.
2. **Completed scope hard-restricted to the 110-113 series.** Even after
   fixing (1), Tracks 125-134 could never appear in "Completed" — a
   deliberate Phase 113X.5 scope boundary for the Advisory Runtime
   chapter that was never widened as later chapters were added. This
   made the stale "Planned: 132F" line look uncontradicted by anything
   above it.
3. **Current-phase identity grammar could not parse a dotted sub-phase
   with a trailing verification letter** (e.g. `"134E.7V"`). Running the
   unmodified generator against the real repository confirmed
   `"in_progress": []` even while the actual current phase was
   `134E.7V` — the current phase silently disappeared from the report
   the moment Track 134 reached its first `.<N>V` verification phase.

A fourth, smaller defect was found while widening scope: `PROJECT_STATUS.md`
gives most phases two `"## Phase X Complete"` headers by convention (a
`"(historical — full text)"` section and a short recap section), which
the unmodified header scan counted independently, producing an
occasional duplicate ID (e.g. `"113V"` appeared twice in
`completed_phase_ids`).

None of these defects were visible from the "Planned: 132F" symptom
alone; each was confirmed independently by running
`build_architecture_status()` against the real repository (see Section
12) and by direct regex inspection, not inferred from the incident
report or a single test file.

## 3. Authority Model

Four separate authorities are established, none inferred from another,
per the Semantic Freshness Invariant:

| Authority | Source | Notes |
|---|---|---|
| Historical completion | `## Phase X Complete` headers in `PROJECT_STATUS.md`, filtered to mainline (non-sub-phase, non-`X`-branch) phase IDs via the existing `_is_milestone_phase_id()` | A phase document existing is not completion evidence by itself — only its own dedicated `## Phase X Complete` header counts, and duplicate headers for the same ID are deduplicated (not double-counted). |
| Current lifecycle state | The `## Current Phase` section's own `"Phase <ID> — <Title> (...)"` declaration line | Read only from within the bounded current-phase section text — never inferred from the completed list, never truncated to a family prefix. |
| Future plan | The current phase section's own `"Recommended next [repo ]phase:"` sentence | Read *only* from the current section — the whole-file fallback that caused the incident is removed entirely. Its absence is disclosed as a limitation, never silently backfilled from history. |
| Runtime state | `pcae.core.runtime_snapshot.build_runtime_snapshot()` | Best-effort; failure is disclosed as a limitation, never silently reused from a stale value. |

Phase-ID parsing and ordering reuse the canonical identity grammar
established by 134B.3's canonical-report-title resolution
(`phase_reports._CANONICAL_TITLE_PHASE_ID_RE`:
`\d+[A-Z](?:\.\d+[A-Za-z]?)*`) rather than introducing a second,
competing phase-identity system — the new
`pcae.core.architecture_status.PHASE_ID_RE` module-level constant is the
same grammar, exposed for parsing/ordering/validation.

Narrative report text (summaries, prose) is never a project-state
authority; the block's own display strings (`completed`, `planned`,
`in_progress`) are always derived from the structured evidence
(`completed_phase_ids`, `current_phase_id`, `planned_phase_ids`), never
the reverse.

## 4. Canonical Project-State Representation

`build_architecture_status()` returns a single structured dict (the
smallest executable representation needed, not a project-management
database):

```
schema_version, state_marker, completed, completed_phase_ids,
completed_chapters, in_progress, current_phase_id, planned,
planned_phase_ids, current_runtime_state, current_maximum_capability,
execution_availability, freshness, limitations, conflicts,
source_provenance
```

`state_marker` is a 16-hex-character SHA-256 digest of the
`PROJECT_STATUS.md` content the status was derived from — a
deterministic repository-state marker with no wall-clock time involved,
so equal content always yields the same marker across processes and
runs. `source_provenance` records, per source, whether it was read
successfully (`"read"`, `"found"`, `"unavailable: <reason>"`,
`"missing"`, `"not_found"`).

## 5. Completed-State Derivation

Completion requires a phase's own `## Phase X Complete` header —
never inferred from a changelog entry, commit message, phase-number
ordering, a previous report's recommendation, document mention alone, or
the current assistant conversation. The 110-113 scope restriction is
removed: every series with genuine header evidence is now included.
Dotted sub-phases and `X`-branch corrective phases are excluded from the
milestone/chapter summary (unchanged from Phase 113X.5 — they are
governance/corrective work, not architecture-track milestones) but
remain visible through their own parent chapter's `phase_ids` once the
parent mainline phase completes; full identity for every completed
phase, including verification and sub-phase IDs, is available by reading
headers directly if a future consumer needs it (out of scope to add
here — see Section 14, non-goals).

Duplicate headers for the same phase ID (this repository's normal
historical + recap convention) are deduplicated by first occurrence. A
conflict is disclosed only when *both* occurrences produce an actually
parsed title (never when one merely falls back to the bare phase ID for
lack of a title line) and the titles disagree.

## 6. Current-State Derivation

The current phase is read only from the `## Current Phase` section's own
declaration line, using the canonical dotted+verification grammar — so
`134E.8`, `134E.8V`, `134E.10`, and `134E.10V` are each preserved exactly
with no prefix matching, no truncation, and no family-only fallback. If
no `## Current Phase` section exists, or its declaration line does not
parse, that is disclosed explicitly via `limitations` rather than
inventing a current phase.

## 7. Planned-State Derivation

Planned phases come only from the current section's own recommendation
sentence. The regex now accepts both the current wording
(`"Recommended next phase:"`) and the retired wording (`"Recommended
next repo phase:"`) — a single pattern, single source of truth — but is
applied **only within the current section's bounded text**; the
whole-file fallback that caused the incident is removed. A completed
phase can never remain planned: any recommendation whose leading phase
ID is already in `completed_phase_ids` is dropped from `planned` and
recorded in `conflicts` (belt-and-suspenders — the primary regex fix
already prevents this in the real repository, but the check remains as a
fail-closed guard against any future stale-recommendation scenario). An
absent recommendation is disclosed as a limitation, not silently
backfilled. There is no optional/committed distinction in the current
source data (`PROJECT_STATUS.md` records exactly one recommendation
sentence per phase); this generator has nothing further to infer and
does not attempt to.

## 8. Architectural Chapter Summarization

One deterministic contract is chosen: **chapter = series** (the leading
digit run of a phase ID), with a concise rendered label plus full
traceability via `completed_chapters: [{chapter, label, phase_ids}]` and
the flat `completed_phase_ids` list.

The pre-existing label renderer (`_render_series_milestone_label`,
Phase 113X.5) computed a *character-level* longest common prefix across
a series' titles. That was correct for the narrow 110-113 dataset it was
verified against (2-3 short, cleanly related titles per series) but,
once the 110-113 restriction was lifted, produced genuinely unreadable
output against real data — e.g. series 122's titles ("...Advisory
Consumption Architecture" vs "...Advisory Context Prototype") share only
`"Con"` at the character level, rendering as `"Con: sumption ... text
Prototype"`. Series with many phases sharing an identical remainder
(e.g. several 119-series titles that reduce to the same "Executable
Schema Implementation:" stem) repeated that stem verbatim per phase,
producing an ever-growing, unreadable line.

Two repairs, applied together:

- `_longest_common_prefix()` now compares whole **words**, never
  splitting inside one — the prefix always ends on a real word boundary.
- `_render_series_milestone_label()` now falls back to a compact,
  bounded form — `"<first phase's title> (<first id>-<last id>, N
  phases)"` — whenever the series has more than 8 phases, has no common
  prefix, produces an empty or duplicate remainder, or the resulting
  line would exceed 200 characters. Full traceability to every
  underlying phase ID is preserved via `completed_chapters`/
  `completed_phase_ids` regardless of which form is used for the label.

This kept every existing 110-113 test fixture's expected output
unchanged (2-3 phase series with clean, distinct remainders) while
producing bounded, readable output for the real repository's much wider
completed history (see Section 12).

## 9. Semantic Freshness

Freshness is one of `fresh`, `fresh_with_limitations`, `stale`,
`invalid` (`pcae.core.architecture_status.VALID_FRESHNESS_STATES`):

- **`invalid`** whenever any conflict was detected (completed/planned
  overlap, a title disagreement between duplicate headers, or
  `PROJECT_STATUS.md` missing).
- **`fresh_with_limitations`** whenever a source was read but a piece of
  state could not be derived (no active phase, no explicit
  recommendation, runtime snapshot unavailable) — the limitation is
  named in `limitations`.
- **`fresh`** only when every authoritative input was read successfully
  and no conflicts or limitations were recorded.
- **`stale`** is reserved for a future caller that persists a status
  alongside a `state_marker` and later detects the current repository
  state marker no longer matches (no caching currently exists in this
  phase — see Section 15 — so `build_architecture_status()` itself never
  emits `stale`; the state is defined for `validate_architecture_status()`
  and any future consumer).

`render_markdown()`'s *"Generated automatically... Never manually
maintained"* claim — the exact sentence whose authority the incident
outstripped — is now conditioned on `freshness == "fresh"`; any other
freshness state renders the freshness value inline and points to the new
Limitations/Conflicts sections instead of asserting unconditional
canonicity.

## 10. Conflict Behavior

Conflicts fail closed (the offending item is dropped from its list) and
are always disclosed in `conflicts`, never silently resolved by picking
"the convenient source": completed/planned overlap, a genuine title
disagreement between duplicate phase headers, and (in
`validate_architecture_status()`) duplicate/invalid phase-ID syntax,
current/completed inconsistency, duplicate or cross-owned chapter
identity, an impossible `Observed` + available-execution runtime
combination, and a `fresh` claim co-occurring with recorded conflicts.

## 11. Ordering

`pcae.core.architecture_status.phase_sort_key()` provides a single
deterministic ordering key: parsable IDs sort by `(series: int, branch:
str, subphase: tuple[(number: int, verification_letter: str), ...])`;
unparsable IDs sort after all parsable ones, by raw string, so a
malformed ID never reorders valid ones around it. Verified directly:

```
["134E", "134E.1", "134E.1V", "134E.2", "134E.8", "134E.10", "134E.10V"]
```

is exactly the order produced regardless of input order, filesystem
enumeration order, or dict iteration order. Ordering is a display
convenience only — it does not imply completion or dependency.

## 12. Runtime-State Derivation

Unchanged mechanism (`build_runtime_snapshot()` via `RuntimeRegistry` /
`HarnessPath`), but failure is now disclosed via `limitations` and
`source_provenance["runtime_snapshot"]` instead of silently leaving the
fields empty with no explanation. No runtime value is hard-coded; if
inspection fails, the fields are left empty and the failure is named.

## 14. Carried 134E.7V Observations (NON-BLOCKING, not repaired here)

None of the following block Architecture Status generation; they are
carried forward unchanged from 134E.7V's independent verification of the
External Delivery Receipt Model, which remains isolated and inactive:

1. Last-attempt-wins silently downgrades a delivered unit if a
   misbehaving caller re-attempts it and it fails. Governed `plan_retry`
   prevents this.
2. `adapter_version` / `renderer_id` / `renderer_version` are not
   enforced equal across retries. Governed path preserves them.
3. Cross-receipt mutual correction/supersession cycles are
   constructible. No global graph; out of scope.
4. Aggregate fields are not semantically re-derived on load. Consistent
   with the 93C digest-only convention.
5. Concurrency is single-process optimistic; last-writer-wins without
   `expected_previous_digest`. Documented limitation.
6. Diagnostic redaction is bounded explicit-pattern, not a universal
   secret scanner. Consistent with established conventions.
7. `save()` enforces count-monotonicity but not prefix-consistency of
   existing attempts; a same-or-greater-count overwrite with different
   content is accepted at the store boundary. The public API
   (`append_attempt`) always preserves the prefix; the opt-in
   `expected_previous_digest` gate is the defense.

## 15. Technical Debt / Future Integration

- No caching exists for `build_architecture_status()`; every call
  re-derives from `PROJECT_STATUS.md` and the runtime snapshot. This is
  deliberate — "prefer no cache over an unsafe cache" — and is cheap
  enough in practice (single-file regex scan) that no cache key/
  invalidation design was needed this phase.
- `completed_chapters`/`completed_phase_ids` currently only carry
  *mainline milestone* phase IDs (matching the pre-existing 113X.5
  convention). A future phase view wanting full traceability to every
  dotted sub-phase and verification phase within a completed chapter
  would need to extend `completed_chapters` with a secondary
  `all_phase_ids` field — deliberately not added here (avoids expanding
  scope beyond the reported defect).
- The structured status dict is designed to be consumed directly (no
  prose parsing) by a future Phase Report View / Operator Report View
  once those views are activated; this phase does not activate them.

## 16. Validation API

`pcae.core.architecture_status.validate_architecture_status(status)`
returns a list of human-readable issues (empty = valid), checking:
supported schema version; unique and syntactically valid phase IDs;
completed/planned disjointness; current/completed consistency; chapter
membership (duplicate identity, cross-chapter phase ownership); runtime
`Observed`/execution-availability consistency; a declared `freshness`
value from the valid set; `fresh` never co-occurring with recorded
conflicts; and that `completed_phase_ids`/`planned_phase_ids` are
already in deterministic `phase_sort_key()` order. It never raises on
malformed input — unexpected shapes are themselves reported as issues.

## 17. Determinism

Verified: repeated calls against the same `PROJECT_STATUS.md` produce
identical output (existing 113X.5 regression, still passing); real
repository `completed_phase_ids` is stable across repeated calls and
already in `phase_sort_key()` order; chapter grouping is independent of
physical header order in the file (113X audit Finding 6, still passing).
No wall-clock time is read into semantic state anywhere in the module.

## 18. Report Integration

`render_markdown()` continues to embed `architecture_status` in the
existing canonical report formatter (the new Rendering Architecture is
not activated, per the non-goals). The structured dict is generated once
per `finalize_phase_report()` call and stored on the `PhaseReport`
instance — the same object is used for both the persisted artifact and
the notification/delivery path, so stored and delivered status cannot
diverge. No change was made to *when* `architecture_status` is
generated relative to report promotion; only *what* it derives.

## 19. Historical-Report Preservation and Transition Point

No historical phase report or `PROJECT_STATUS.md` history section was
rewritten. The repair takes effect for every report generated **from
this phase's commit forward** — the transition point is the commit that
lands this change. Prior reports remain historical evidence of what
operators actually received at the time, unchanged.
