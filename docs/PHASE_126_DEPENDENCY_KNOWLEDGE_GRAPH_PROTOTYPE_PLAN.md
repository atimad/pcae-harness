# Phase 126D - Dependency Knowledge Graph Prototype Plan

## 1. Objective

Phase 126D defines the definitive implementation plan for the first
deterministic, read-only Dependency Knowledge Graph Builder, bounded
by the 126B contract and independently verified in 126C.

The builder shall consume existing Repository Intelligence artifacts
only — a Repository Knowledge Snapshot, reached exclusively through
the Track 121 Query Layer — and shall produce a deterministic
Dependency Knowledge Graph artifact conforming to the already-frozen
119S/119T schema.

This phase is documentation only. It implements no graph generation,
modifies no runtime behavior, and creates no source code, test code,
or schema change. 126E implements the plan defined here; 126D performs
none of it.

## 2. Grounding This Plan in the Real Generator

Unlike 126A/126B, which reasoned about Repository Knowledge Snapshot
conceptually, 126D grounds every mapping decision below in the actual
behavior of the existing Track 120 generator
(`src/pcae/repository_intelligence/snapshot_builder.py`), read
directly for this plan. This surfaces a fact neither 126A nor 126B
identified: **Repository Knowledge Snapshot's `entity_type` vocabulary
(119O/119P) and the Dependency Knowledge Graph's `node_type` vocabulary
(119S/119T) are two different, non-identical enums.**

- RKS `entity_type` enum: `document`, `schema`, `package`, `module`,
  `command`, `configuration`, `test`, `task`, `phase`, `release`,
  `runtime_component`, `advisory_component`, `evidence_artifact`,
  `repository_skill`, `contract`, `report`, `source_file`, `unknown`.
- DKG `node_type` enum (126B §4.2): `repository`, `package`, `module`,
  `file`, `document`, `schema`, `command`, `configuration`, `test`,
  `task`, `phase`, `release`, `runtime_component`,
  `advisory_component`, `evidence_artifact`, `repository_skill`,
  `contract`, `unknown`.

RKS has `report` and `source_file`, which DKG does not. DKG has
`repository` and `file`, which RKS does not. A graph builder consuming
RKS entities and producing DKG nodes must therefore perform an
explicit `entity_type` → `node_type` translation step — this was not
previously identified in 126A or 126B and is this plan's first
concrete addition.

Further, the real generator's own classification logic
(`_entity_type_for`) currently produces only a narrow subset of its
schema's own permitted values in practice: `module` for top-level
directories under `src/pcae/{commands,core}`, `source_file` for `.py`
files within them, plus fixed-path `test` and `schema` entities for
`tests/` and `schemas/repository_intelligence/`. No current snapshot
ever contains `package`, `report`, `document`, `command`,
`configuration`, `task`, `phase`, `release`, `runtime_component`,
`advisory_component`, `evidence_artifact`, `repository_skill`, or
`contract` entity instances, even though the RKS schema permits them.
126E's builder must handle the full permitted enum (for future
generator growth) but should expect, in practice, to translate mostly
`module`, `source_file`, `test`, and `schema` entities from any
snapshot generated by the current Track 120 implementation.

## 3. Prototype Scope

Implementation plans below cover: graph builder, graph serialization,
graph validation, graph persistence, graph metadata, provenance
propagation, limitation propagation, boundary propagation, and
deterministic output. None of these is implemented in this phase.

## 4. Inputs

The builder shall consume only:

- an existing **Repository Knowledge Snapshot** artifact;
- reached exclusively through the **Repository Intelligence Query
  Layer** (Track 121) — specifically, entity lookup and attribution
  lookup query categories, applied exhaustively over the snapshot's
  declared entity set (not ad hoc per-name lookups), plus limitation
  and boundary lookup categories for the snapshot-level material the
  graph must propagate (Section 8).

No repository scanning beyond what Track 120's already-approved
Repository Knowledge Snapshot generation performs. The builder never
reads repository files directly, never reruns the Track 120 generator,
and never queries anything the Track 121 Query Layer does not already
expose.

## 5. Graph Model (Entity/Node and Relationship/Edge Mapping)

### 5.1 Node Category Mapping (`entity_type` -> `node_type`)

Resolving the brief's conceptual node list against both the frozen DKG
`node_type` enum (126B §4.2-4.3) and the real RKS `entity_type`
vocabulary (Section 2), binding for 126E:

| Conceptual category (this phase's brief) | RKS `entity_type` source | DKG `node_type` target | Notes |
| --- | --- | --- | --- |
| repository | *(none — see below)* | `repository` | Synthesized once per graph from the snapshot's own repository/envelope identity, not from an RKS entity list item (RKS has no `repository`-typed entity). |
| directory | `module` (Track 120's actual convention) | `module` | Track 120 currently classifies every top-level source directory as `entity_type: module`, not `package`. 126E must follow this existing convention, not invent a `directory`-specific mapping the real generator doesn't produce. |
| file | `source_file` | `file` | Direct translation; RKS's `source_file` becomes DKG's `file`. |
| module | `module` | `module` | Same RKS source as "directory" above — see the terminology note below. |
| class | *(not produced by RKS today)* | *(out of v1 scope)* | Per 126B §4.3, deferred entirely — RKS does not extract class-level entities, so the builder has no source-attributed basis. |
| function | *(not produced by RKS today)* | *(out of v1 scope)* | Same as class — deferred per 126B §4.3. |
| artifact | `evidence_artifact` | `evidence_artifact` | Direct translation. |
| schema | `schema` | `schema` | Direct translation. |
| command | `command` | `command` | Direct translation (not yet produced by the real generator, but schema-permitted). |
| runtime component | `runtime_component` | `runtime_component` | Direct translation (not yet produced by the real generator, but schema-permitted). |
| documentation entity | `document` | `document` | Direct translation (not yet produced by the real generator, but schema-permitted). |
| *(additional RKS values not in the brief's list)* | `package`, `configuration`, `task`, `phase`, `release`, `advisory_component`, `repository_skill`, `contract` | same-named `node_type` value | Direct 1:1 translation; all these RKS values have an identically-named DKG value. |
| *(RKS-only value)* | `report` | `evidence_artifact` | Per 126B §4.3's report->evidence_artifact resolution. |
| *(unclassifiable)* | `unknown` | `unknown` | Direct translation; never silently upgraded to a more specific type. |

**Terminology note (new finding, not previously surfaced in 126A/126B):**
Track 120's use of `module` for *directories* means a DKG `module` node
sourced from a real snapshot today represents a source directory
(e.g. `src/pcae/commands/`), not a Python module file in the
conventional sense (a `.py` file is a `file` node, per the `source_file`
mapping above). 126E's builder must not relabel or reinterpret this —
it must propagate Track 120's own entity classification exactly as
declared, including this existing (and, from a plain-English reading,
slightly surprising) naming convention. Any future desire to
distinguish "directory" from "Python module" as separate node
categories is a Track 120 (Repository Knowledge Snapshot) scoping
question, not a Track 126 one — 126B §7's "the graph must not modify
Track 120" rule applies directly.

### 5.2 Edge Category Mapping

Resolving the brief's conceptual edge list against the frozen DKG
`edge_type` enum and 126B §5.2's resolutions, binding for 126E:

| Conceptual category (this phase's brief) | DKG `edge_type` target | Extraction basis |
| --- | --- | --- |
| contains | `related_to` (126B §5.2) | A directory-typed (`module`) entity's declared child path relationship to a file/module entity nested under it, derived from `entity_path` prefix structure already present in RKS content. Carries the v1 containment-precision limitation 126B §5.2 requires documenting on every such edge. |
| references | `references` | Direct — any RKS-declared cross-entity reference (e.g. a documentation entity's declared reference to a schema entity) already captured by existing RKS source attribution/reference fields. |
| imports | `depends_on` (126B §5.2) | Deferred to a future RKS extraction enhancement — the current Track 120 generator does not parse import statements (its own limitation record: "does not parse file contents, imports, or symbols"). **126E's v1 builder therefore produces zero `imports`-derived edges from any snapshot generated by the current Track 120 implementation** — this is not a Track 126 limitation, it is inherited directly from Track 120's own declared scope, and must be propagated as a limitation, not silently worked around. |
| depends_on | `depends_on` | Direct, for any future RKS content that declares a dependency relationship explicitly (none does today; see above). |
| produces | `produces` | Direct, for any future RKS content declaring a producer relationship (e.g. a command entity that produces an artifact entity), where such a relationship is already explicit in RKS source attribution. |
| consumes | `consumes` | Direct, symmetric to `produces`. |
| implements | `depends_on` (126B §5.2, dual-use) | Direct, where RKS content declares an entity conforming to a contract entity. |
| validates | `verifies` (126B §5.2) | Direct, where RKS content declares a test entity's declared relationship to the entity it tests (e.g. the `tests` directory entity's relationship to `src/pcae` entities, if and when RKS makes this explicit — not currently produced). |
| documents | `documents` | Direct, where a document-typed entity declares a relationship to the entity it documents. |
| related_to | `related_to` | Direct, generic fallback for any declared structural association not covered by a more specific type above. |

**Critical v1 scope finding:** because the current Track 120 generator
only ever produces `module`/`source_file`/`test`/`schema` entities with
no declared cross-entity relationships beyond path containment, **the
first Dependency Knowledge Graph Builder, run against any snapshot the
current Track 120 implementation can produce, will generate `contains`
(`related_to`)-derived edges from path structure and effectively zero
other edge types** — not because the builder is incomplete, but
because RKS itself does not yet declare richer relationships to derive
from. This must be stated explicitly in the graph's own limitations
(Section 8), not treated as a builder defect. Every edge category the
builder implements support for remains ready to activate the moment a
future Track 120 enhancement declares the relationship RKS-side — no
Track 126 change is required when that happens.

### 5.3 No Inference, No Reasoning, No Probabilistic Relationships

Consistent with 126B §10 (Determinism Contract) and §12 (Failure
Contract), the builder shall never infer a relationship the underlying
RKS content does not explicitly support. If RKS content does not
declare a relationship, the builder omits it — it does not guess an
`imports` edge from a plausible-looking file name, does not infer a
`depends_on` edge from directory proximity, and does not apply any
heuristic, scoring, or AI-based judgment anywhere in extraction.

## 6. Graph Construction Pipeline (Planned Stages)

126E shall implement the following twelve stages. Each is a planned
responsibility; 126D performs none of them.

1. **Input validation** — confirm the supplied Repository Knowledge
   Snapshot reference resolves to an existing, schema-valid artifact
   via the Query Layer before any extraction begins; fail closed
   (Section 10) on an invalid or missing reference.
2. **Repository Intelligence loading** — issue Query Layer requests
   (entity lookup across the full declared entity set, attribution
   lookup, limitation lookup, boundary lookup) to obtain the complete
   snapshot content the builder needs; never read the snapshot file
   directly.
3. **Entity extraction** — enumerate every RKS entity and apply the
   Section 5.1 `entity_type` -> `node_type` mapping table
   deterministically.
4. **Relationship extraction** — apply the Section 5.2 mapping table to
   every RKS-declared relationship (today: path-containment only, per
   Section 5.2's critical finding) to produce candidate edges.
5. **Graph construction** — assemble the node and edge collections plus
   `dependency_claims` (one `node_existence` claim per node, one
   `edge_existence` claim per edge, per the frozen schema's
   `dependency_claim` shape), using the stable identifier scheme
   (Section 7).
6. **Metadata attachment** — populate `graph_metadata`: `graph_id`,
   `graph_name`, `graph_kind` (`dependency`, per the frozen
   `graph_kind` enum), `graph_scope`, `graph_directionality`
   (`directed`, since `depends_on`/`references`/etc. are inherently
   directional; `contains`-derived `related_to` edges may set their own
   per-edge `direction` independently), `graph_completeness_state`
   (Section 9, resolving 126C Finding 3), `node_count`, `edge_count`,
   and `graph_generation_method_disclosure` (resolving 126A §9A —
   an honest, specific description naming this exact builder and its
   deterministic extraction rules).
7. **Provenance attachment** — populate `source_attribution` on every
   node, edge, and claim, citing the specific RKS entity/attribution
   record each was derived from (never a generic "the snapshot"
   citation).
8. **Limitation attachment** — populate `snapshot_limitations`
   (inherited unchanged from the source RKS, per 126B §8) plus
   graph-specific added limitations (v1 containment-precision limit,
   v1 class/function exclusion, v1 "no `imports` edges" limit — Section
   5.2).
9. **Boundary attachment** — populate `boundary_disclosures` and the
   frozen `dependency_knowledge_graph_snapshot_disclaimer` const
   string, unchanged.
10. **Graph validation** — Section 8 below.
11. **Deterministic serialization** — Section 9 below.
12. **Persistence** — write the graph artifact via a
    `persistence.py`-style module distinct from Track 120's own
    (mirroring, not modifying, the existing pattern), storing it
    separately from the source Repository Knowledge Snapshot.

## 7. Stable Identifier Algorithm (Resolving 126C Finding 1)

126C Finding 1 required 126D to explicitly extend node-identifier
determinism to `edge_id`. This plan resolves it:

- **`node_id`**: `f"node:{entity_path}"`, mirroring Track 120's own
  `entity_id = f"entity:{entry.relative_path}"` convention exactly —
  deterministic (a pure function of the RKS entity's own path), stable
  (identical across repeated generation), and unique (RKS entity paths
  are already unique within a snapshot).
- **`edge_id`**: `f"edge:{edge_type}:{source_node_id}->{target_node_id}"`
  — deterministic (a pure function of the edge's own type and
  endpoints), stable (identical across repeated generation from the
  same snapshot), and unique (no two edges may share the same type and
  endpoint pair in a single graph; where RKS content could otherwise
  produce a duplicate, the builder fails closed per Section 10 rather
  than silently deduplicating or suffixing).

Both identifier schemes are applied uniformly — the same determinism/
stability/uniqueness standard 126B §4.4 required for `node_id` alone
now explicitly covers `edge_id` too, closing 126C Finding 1 without
requiring any amendment to 126B itself.

## 8. Validation Strategy

126E's graph validation stage (pipeline stage 10) shall check, and
fail closed (Section 10) on any violation:

- **Unique node identifiers** — no two nodes share a `node_id`.
- **Unique edge identifiers** — no two edges share an `edge_id`
  (Section 7).
- **Valid edge endpoints** — every edge's `source_node_id` and
  `target_node_id` resolve to an actual node in the same graph; no
  dangling edge references.
- **Valid node categories** — every node's `node_type` is a member of
  the frozen enum (Section 5.1's mapping table guarantees this by
  construction, but validation re-checks it independently rather than
  trusting the mapping step).
- **Valid edge categories** — symmetric check for `edge_type`.
- **Deterministic ordering** — nodes and edges are serialized in a
  stable sort order (e.g. lexicographic by `node_id`/`edge_id`),
  consistent with 126B §10's ordering requirement.
- **Metadata completeness** — every `graph_metadata` required field
  (Section 6, stage 6) is present and non-empty.
- **Provenance completeness** — every node, edge, and claim has at
  least one `source_attribution` record (schema-required,
  independently confirmed by 126C).
- **Limitation completeness** — every node, edge, claim, and the
  snapshot as a whole has at least one limitation record
  (schema-required `minItems: 1`).
- **Boundary completeness** — `boundary_disclosures` and
  `disclaimers` are both present with their required const fields.

Any validation failure causes the builder to refuse to produce output
(Section 10) rather than emit a partially-valid artifact.

## 9. Serialization Strategy (Resolving 126C Finding 2)

126D adopts Track 124's existing `serialize_deterministic_json` helper
(`src/pcae/repository_intelligence/serialization.py`) for the graph
artifact's JSON output, rather than reintroducing parallel
serialization logic — directly resolving 126C Finding 2's
recommendation. This helper already provides: `indent=None` for
compact output, `indent=2` for pretty output, and `sort_keys=True` for
deterministic key ordering, exactly matching 126B §10's determinism
requirement with zero new code needed for the serialization layer
itself.

**Equivalent Repository Intelligence inputs shall produce equivalent
Dependency Knowledge Graph outputs, except approved timestamps.**
Concretely: given the same source Repository Knowledge Snapshot, two
independent runs of the builder must produce byte-identical JSON output
for every field except `envelope.generated_at_utc` (and any other
already-established non-load-bearing timestamp field inherited from
the common artifact envelope) — matching the same "timestamps are
non-load-bearing" principle every prior Repository Intelligence
artifact family has held since Track 119's conceptual schema
architecture.

126D also adopts Track 124's shared `consumer_validation.py` helpers
(`validate_query_result_shape`, `ensure_records_have_attribution`,
`ensure_limitations_present`, `ensure_boundary_material_present`) for
the builder's own Query Layer result validation at pipeline stage 1-2,
rather than reintroducing parallel validation logic — the second half
of 126C Finding 2's resolution.

## 10. Failure Strategy

The builder shall fail closed — refuse to produce output — for:

- **Invalid Repository Intelligence artifacts** — a Query Layer result
  that does not satisfy the shared `validate_query_result_shape`
  check (Section 9).
- **Unsupported schema versions** — a source snapshot whose
  `executable_schema_version` the builder does not recognize.
- **Missing provenance** — any candidate node, edge, or claim lacking
  `source_attribution`.
- **Missing limitations** — any candidate node, edge, claim, or the
  snapshot as a whole lacking at least one limitation record.
- **Missing boundary disclosures** — absent `boundary_disclosures` or
  `disclaimers` material from the Query Layer result.
- **Duplicate node identifiers** — Section 8.
- **Duplicate edge identifiers** — Section 8.
- **Invalid references** — an edge whose endpoint does not resolve to
  a real node (Section 8).
- **Serialization failures** — any error during the
  `serialize_deterministic_json` call (e.g. a non-serializable value
  reaching the serializer, which validation should have already
  prevented) aborts artifact production rather than emitting malformed
  output.

No fail-open path exists anywhere in this plan. This directly
implements 126B §12's Failure Contract for the concrete v1 builder.

## 11. Verification Strategy (What 126F Shall Verify)

126F shall independently verify:

- **Deterministic generation** — two independent builder runs against
  the same source snapshot produce byte-identical graph output (except
  approved timestamps).
- **Schema compliance** — every generated graph artifact validates
  against the frozen `dependency_knowledge_graph_snapshot.schema.json`
  (119S/119T), unmodified.
- **Graph validity** — every Section 8 validation check independently
  re-confirmed against real generated output, not just re-read from
  the builder's own claims.
- **Regression compatibility** — Tracks 120-124's existing regression
  suites remain unaffected (the builder is a new, additive module; it
  must not require any change to `snapshot_builder.py`, the Query
  Layer, Advisory Context Builder, or Change Impact Builder).
- **Attribution preservation** — every generated node/edge/claim's
  source attribution independently traced back to real RKS entity
  content.
- **Limitation preservation** — inherited RKS limitations independently
  confirmed present unchanged in generated output, alongside the
  graph-specific added limitations (Section 6, stage 8).
- **Boundary preservation** — boundary disclosures and the frozen
  disclaimer const string independently confirmed present unchanged.
- **Serialization compatibility** — independently confirmed that
  `serialize_deterministic_json` reuse (Section 9) produces the same
  compact/pretty/sorted-key behavior as every other Repository
  Intelligence artifact family.
- **Fail-closed behavior** — independently probed against at least one
  scenario per Section 10 failure category, confirming the builder
  refuses output rather than degrading gracefully into a partial
  artifact.

## 12. Incorporation of 126C Findings

All three 126C findings are explicitly resolved within this plan, not
deferred further:

- **Finding 1 (edge identifier stability)**: resolved in Section 7 —
  the stable identifier algorithm now explicitly and symmetrically
  covers both `node_id` and `edge_id`.
- **Finding 2 (Track 124 compatibility)**: resolved in Section 9 — the
  builder explicitly reuses `serialize_deterministic_json` and the
  shared `consumer_validation.py` helpers rather than reintroducing
  parallel logic.
- **Finding 3 (`graph_completeness_state` not explicitly required)**:
  resolved in Section 6, pipeline stage 6 — `graph_metadata.graph_
  completeness_state` is an explicit, named output of the metadata-
  attachment stage. Given Section 2's grounding (the current Track 120
  generator covers only a narrow fixed set of top-level paths), 126E's
  builder must honestly set this field to `partial` for any graph
  derived from a current-generation snapshot — never
  `complete_claimed_by_source` — consistent with 126B §7's general
  honesty requirement this finding was originally anchored to.

## 13. Compatibility

This plan remains compatible with, and modifies none of:

- **Track 119 schemas** — the builder consumes and produces only the
  already-frozen schemas; no schema file is touched by this plan or by
  126E.
- **Track 120 Repository Knowledge Snapshot** — the builder's only
  input, reached exclusively through the Query Layer; not modified.
  Section 2's `entity_type` findings describe Track 120's *existing*
  behavior for planning purposes; they do not propose changing it.
- **Track 121 Query Layer** — the builder's only access path; not
  modified. This plan does not scope new Query Layer categories for the
  graph itself (126A §7's anticipated future query categories remain
  unscoped and unauthorized here, consistent with 126B §11).
- **Track 122 Advisory Context Builder** — not modified; not consumed
  by 126E's builder.
- **Track 123 Change Impact Builder** — not modified; not consumed by
  126E's builder. The graph artifact 126E produces is available for a
  future, separately governed Change Impact revision to consume, but
  no such revision is scoped or authorized here.
