# Phase 130D - Cross-Artifact Knowledge Integration Prototype Plan

## 1. Purpose

This phase produces the definitive, bounded implementation plan for
130E - the first deterministic, read-only Cross-Artifact Knowledge
Integration prototype. It defines what 130E may build, from what
inputs, using what strategy, satisfying what acceptance criteria, and
verified how in 130F. This phase performs no implementation itself:
no schema, source, or test file is touched by 130D.

130C found the frozen 130B contract internally consistent, source-
accurate, and free of blocking defects, with four carried-forward
findings (130C §21) and one significant independent discovery: Change
Impact's own frozen executable schema (`119U`) already contains
`dependency_context`/`dependency_context_reference` fields whose
`context_type` enum already includes `graph_node`/`graph_edge` -
unpopulated by the real builder, but structurally ready. This plan's
central strategic decision follows directly from that discovery:
**no new schema shall be invented where an existing executable schema
already provides the required structure.**

## 2. Prototype Scope

The 130E prototype integrates existing verified artifacts only. It
introduces:

- **no reasoning** - no interpretation of what a connection means;
- **no inference** - no relationship not directly derivable from an
  existing stable identifier already present in both endpoints;
- **no recommendations** - no ranking, prioritization, or suggested
  action;
- **no Decision Evaluation** - the prototype is not, and does not
  invoke, Decision Evaluation;
- **no execution planning** - out of scope entirely;
- **no execution capability** - the prototype executes nothing;
- **no runtime plugins** - none registered, none required.

The prototype's entire value is structural: it connects what already
exists, using identifiers that already exist, producing an artifact
that is itself read-only and re-derivable from its inputs.

## 3. Inputs

Only verified, already-implemented artifacts may be consumed:

- **Repository Knowledge Snapshot** (Track 120, `119O`) - via `pcae
  repository-intelligence snapshot generate`'s output, read directly
  as a file path, exactly as every existing consumer (Historical
  Memory, Advisory Context, Change Impact) already does.
- **Dependency Knowledge Graph** (Track 126, `119S`) - read directly
  as a file path.
- **Historical Memory** (Track 127-128, `119Q`) - read directly as a
  file path.
- **Change Impact** (Track 123, `119U`) - read directly as a file
  path.
- **Advisory Context** (Track 122, `119W`) - read directly as a file
  path.
- **Query Layer artifacts, where appropriate** - the Query Result
  envelope (`119Y`) may be consumed where an existing artifact is
  reached through the Query Layer rather than a direct file path
  (matching Historical Memory's own existing precedent of reaching
  Repository Knowledge Snapshot content exclusively through
  `execute_query()`/`load_snapshot()`).

No artifact family outside these six is consumed. No artifact is
regenerated by the prototype - each of the six remains independently
generated by its own existing, unmodified CLI command.

## 4. Output

A deterministic integrated knowledge package. Per 130B §5's conceptual
model (unchanged, not amended by this plan):

- **entirely derivative** - every field traces to one or more of the
  six input artifacts;
- **references only** - no restated content, only pointers (artifact
  reference + entity reference, 130B §5) plus the minimum surrounding
  context (provenance, uncertainty, limitation, boundary material)
  required to interpret the reference honestly;
- **never independent knowledge** - the package asserts nothing that
  is not already asserted, verbatim, by one of its six source
  artifacts.

This plan does not authorize a new schema for this output artifact.
Section 6's architectural simplification further reduces how much new
structure, if any, a future schema-authoring phase would even need to
define.

## 5. Integration Strategy

Three governing principles, binding for 130E:

1. **Reuse existing stable identifiers.** Every cross-artifact
   reference resolves via a real, already-declared identifier field
   (`entity_id`, `node_id`, `event_id`/`claim_id`/etc.,
   `impact_claim_id`) - never a newly minted one (130B §5, 130C §5
   independently re-confirmed all four).
2. **Reuse existing executable schemas whenever possible.** Section 6
   is the concrete, load-bearing instance of this principle: Change
   Impact's own `119U` schema already has the structure this prototype
   needs for its single most concrete relationship category. Where a
   future 130E population target has no existing schema field (e.g.
   RKS-to-DKG entity correspondence, 130C §6's own finding that no
   such field exists on either side today), the prototype does not
   invent one - it either defers that specific connection to a later
   phase or represents it as an explicit uncertainty record (Section
   10), never a schema workaround.
3. **Explicitly avoid introducing parallel concepts already
   represented elsewhere.** If a concept already has a name and a
   field in an existing frozen schema (e.g. `verification_state`,
   `limitations`, `source_attribution`, `dependency_context_
   reference`), 130E reuses that name and that field - it does not
   define a same-meaning-different-name construct anywhere in its own
   output or its own internal code.

## 6. Change Impact Integration (Architectural Simplification)

130C independently confirmed, by direct schema inspection, that
`change_impact_report.schema.json` already declares:

- a top-level `dependency_context` array of `dependency_context_
  reference` objects (`context_id`, `context_type`, `reference_
  locator`, `source_attribution`, `limitations` - all already
  required fields on the existing `$def`);
- `context_type`'s enum already including `"dependency_knowledge_
  graph_snapshot"`, `"graph_node"`, `"graph_edge"`, `"dependency_
  claim"`, `"unknown"`;
- `impact_claim.dependency_context_reference` - a nullable string
  field on every impact claim, presumably intended to hold a
  `context_id` from the `dependency_context` array.

**This is a genuine architectural simplification for 130E, not a
workaround.** The prototype's plan for Change Impact <-> Dependency
Knowledge Graph integration is: **populate these existing fields**,
not design new ones. Concretely, 130E's bounded implementation task
for this specific integration point is:

1. For a given Change Impact Report and a given Dependency Knowledge
   Graph Snapshot (both already generated, both read as inputs per
   Section 3), determine which `affected_entity.entity_id` values
   (already present on every impact claim's affected entities, 130C
   §6) correspond to a DKG `node_id` - only where Repository Knowledge
   Snapshot's own `entity_id` and DKG's own `node_id` can be
   deterministically connected via an already-existing, already-
   populated field on one side or the other (Section 8's identity
   strategy governs exactly how strict this must be - no fuzzy
   bridging is authorized even here).
2. Where such a connection is deterministically resolvable, populate
   a `dependency_context_reference` entry (`context_type:
   "graph_node"`, `reference_locator` citing the DKG `node_id`,
   `source_attribution` citing the DKG snapshot's own identity) and
   set the relevant `impact_claim.dependency_context_reference` to
   its `context_id`.
3. Where not resolvable, the field remains unpopulated (its current,
   already-correct, honest state) - not filled with a best-guess
   value.

**This document itself does not implement this population logic.**
130E implements it; 130D only plans it, and explicitly documents this
as an architectural simplification: no new integration-package schema
field is needed for this specific relationship category, because the
target schema already has one, sitting unused.

## 7. Historical Integration

Historical Memory records shall reference current repository entities
without creating inferred history. Concretely:

- Historical Memory's own `historical_reference.reference_type` enum
  (independently re-confirmed present, `119Q`) already includes
  `"artifact"` as a value, but 127D-128F all independently confirmed
  this is unpopulated in the real builder - unchanged by this plan.
- 130E's bounded task, if it touches Historical Memory integration at
  all in its first prototype (Section 15's acceptance criteria scope
  this explicitly), is limited to: given a Historical Memory Snapshot
  and a Repository Knowledge Snapshot, connect a `phase_lineage_
  record.phase_id` (or equivalent already-declared identifier) to an
  RKS `entity_id` only where the underlying task-contract-derived
  provenance already, deterministically, names that entity - never by
  inferring that a historical phase "probably relates to" a current
  entity based on similarity, timing, or narrative plausibility.
- **No inferred history**: if no deterministic connection exists, the
  historical record remains exactly as generated by Historical
  Memory's own existing builder - the integration layer adds no
  interpretation, timeline, or narrative Historical Memory itself does
  not already assert.

## 8. Dependency Integration

Dependency Knowledge Graph entities become reference targets only.

- **No traversal.** 130E's Dependency Knowledge Graph consumption is
  limited to reading individual `graph_node`/`graph_edge` records by
  their own already-declared `node_id`/edge identifier - it never
  walks the graph structure to discover multi-hop relationships. This
  restates 130A §8/130B §6's own "graph correspondence... derivable
  today from existing schema content" scoping and 126A's own
  original "no traversal" boundary, unchanged.
- **No reasoning.** A DKG entity referenced by the integration layer
  carries no added interpretation of what its structural position in
  the graph means - it is cited, not analyzed.

## 9. Advisory Integration

Deterministic context assembly only - restating Advisory Context's
own existing, unchanged non-authority boundary (Tracks 122/123's
precedent). 130E's Advisory Context consumption, if included in the
first prototype's bounded scope (Section 15), is limited to
referencing an Advisory Intelligence Context Package's own already-
assembled entity citations - never adding new interpretation on top
of what Advisory Context itself already assembled. **This plan does
not introduce richer Advisory reasoning** - Advisory Context's own
generator, consumption boundary, and output shape remain entirely
unmodified by Track 130.

## 10. Query Relationship

The prototype prepares future unified querying (Track 131) by
producing an artifact structurally suited to being queried later - a
deterministic, schema-shaped, read-only package with stable
identifiers throughout. **Track 130 itself shall not expand the Query
Layer.** `SUPPORTED_QUERY_CATEGORIES` (currently six, RKS-only,
independently re-confirmed unchanged in 130C §13) is not touched by
130D or by any phase in Track 130's own planned sequence (130A-130F,
Section 20).

## 11. Provenance Strategy

Every integrated reference shall preserve, unchanged from 130B §8:

- **originating artifact** - which specific source artifact instance
  (its own `snapshot_identity`/`executable_schema_version`);
- **originating record** - the specific entity/record referenced;
- **source locator** - the referenced entity's own existing `source_
  locator`/`source_attribution` content, carried forward, never
  regenerated;
- **derivation path** - the reconstructable chain from the integrated
  reference back to source content;
- **verification state** - the referenced entity's own existing
  `verification_state`, carried forward unchanged;
- **schema version** - the source artifact's own `executable_schema_
  version`.

130E's implementation must supply all six for every reference it
creates, or fail closed for that reference (Section 16) - this plan
authorizes no partial-provenance output path.

## 12. Identity Strategy

- **Reuse existing identifiers.** Every reference cites a real,
  already-declared identifier field from its target artifact.
- **Never create replacement identifiers.** 130E does not mint a new
  "integration ID" that substitutes for or aliases an existing
  `entity_id`/`node_id`/`event_id`/`impact_claim_id` - it cites the
  original directly.
- **Never merge identities.** Where two artifacts might plausibly
  describe the same real-world thing but no existing field
  deterministically connects them (130C §6's own finding for entity/
  graph/historical/advisory correspondence generally), 130E does not
  merge them into one integration-layer identity - each remains
  separately referenced, connected only where Section 6/7/8 above
  already establish a deterministic path exists.

## 13. Uncertainty Strategy

Carry uncertainty unchanged - no uncertainty reduction. Per 130C §9's
own finding (carried forward, Section 19 below), 130E's actual
implementation must use the *real* existing enum vocabularies for the
four concepts that already have literal schema matches (`unknown`,
`incomplete`, `conflicting` from `state_value`/`completeness_state`;
`unresolved` from `resolution_state`), and must not claim
`"unavailable"`/`"unsupported"` are carried-forward literal tokens
since no source schema declares them as such - 130E instead expresses
those two concepts via existing free-text limitation/note fields
(`limitations`, `boundary_notes`) rather than inventing new enum
values, consistent with Section 5's "reuse existing schemas" principle
and 130C's own resolution recommendation.

## 14. Limitation Strategy

Propagate all limitations unchanged - every inherited limitation from
every referenced artifact appears, verbatim in substance, wherever the
integration layer surfaces content derived from that artifact.
Integration-specific limitations (describing integration-layer
boundaries only, e.g. "this prototype does not resolve
`current_entity_has_history` for entities lacking a task-contract-
derived introduction commit") may be added, never substituted for an
inherited one.

## 15. Boundary Strategy

Propagate all boundary disclosures unchanged from every referenced
artifact's own existing `boundary_disclosure` material (the shared
nine-field component, 130C §11). Per 130C §11's own finding (carried
forward, Section 19), the two conceptual disclosures with no existing
dedicated field ("derivative nature," "human approval unchanged") are
expressed via the existing free-text `boundary_notes` array in 130E's
prototype - this plan does not authorize adding new `const: true`
boundary fields, since that would require a schema change out of
Track 130's current authorization.

## 16. Determinism Strategy

Equivalent verified inputs produce equivalent integrated outputs
except approved timestamps (the same two-field non-load-bearing
convention every artifact family already uses). 130E's implementation
must be independently re-verifiable via the same two-independent-runs
byte-comparison method every prior artifact family's own prototype
phase has already established (127E, 126E, and re-confirmed multiple
times for Historical Memory in 127F/128F) - 130F re-runs this
comparison independently (Section 21), not merely trusts 130E's own
claim of it.

## 17. Serialization Strategy

Reuse existing deterministic serialization helpers - specifically
`serialize_deterministic_json` (`src/pcae/repository_intelligence/
serialization.py`), already reused unchanged by Dependency Knowledge
Graph and Historical Memory (Track 124's own hardening precedent, and
128E/128F's own confirmation this reuse remains unchanged). **Avoid
duplicate implementations** - 130E introduces no parallel
serialization logic; if the existing helper's output shape needs any
adjustment for this artifact family, that is a finding for a future,
separately scoped phase, not something 130E works around locally.

## 18. Failure Strategy

Fail closed - restating 130B §17 unchanged, binding for 130E's actual
implementation:

- **no inferred recovery** - a missing or invalid source artifact
  (any of the six, Section 3) halts generation for the affected scope,
  never silently substituted or worked around;
- **no silent omission** - an entity or relationship that fails a
  validation or identity-resolution check produces either an explicit
  failure or an explicit uncertainty/gap record (Section 13), never a
  quiet drop with no trace.

## 19. Four Carried-Forward Findings - Explicit Resolution

Every finding from 130C §21 is resolved here, none silently ignored:

1. **Uncertainty vocabulary precision** (130C §9/§21.1) - **Resolved**
   by Section 13 above: 130E uses the real existing enum vocabularies
   for the four concepts with literal matches, and expresses the two
   without literal matches (`unavailable`, `unsupported`) via existing
   free-text fields rather than inventing new enum tokens.
2. **Boundary disclosure field mapping** (130C §11/§21.2) -
   **Resolved** by Section 15 above: the two unmapped conceptual
   disclosures are expressed via the existing `boundary_notes`
   free-text array; no new schema field is introduced, preserving
   Track 130's current no-schema-change scope.
3. **Impact correspondence's existing schema anchor** (130C §6/§21.3)
   - **Resolved** by Section 6 above: explicitly adopted as 130E's
   primary, concrete, bounded implementation target - the
   architectural simplification this entire plan is built around, per
   this phase's own governing instruction.
4. **Provenance linkage terminology** (130C §6/§21.4) - **Resolved**
   by this plan's own Section 11 framing: provenance linkage is
   treated throughout this document as the underlying mechanism every
   reference and relationship depends on (Section 11), not listed as
   a peer relationship category alongside entity/historical/graph/
   impact/advisory correspondence and artifact lineage (Section 6-9).

No 130C finding is deferred without an explicit resolution decision
recorded above.

## 21. Independent Verification Strategy (for 130F)

130F shall independently verify, not trust 130E's own implementation
tests:

- **schema conformance** - against every one of the six input
  artifacts' own frozen schemas, using an independent, from-scratch
  validation approach (mirroring 128F's own dependency-free recursive
  validator, since no `jsonschema` library is available anywhere in
  this environment - confirmed unchanged this session);
- **deterministic output** - two independently generated fresh
  integration packages from the same fresh set of six input artifacts,
  compared byte-for-byte except approved timestamps (Section 16);
- **provenance preservation** - every integrated reference's six
  required elements (Section 11) independently spot-checked against
  its cited source artifact's own real content;
- **identifier preservation** - every cited identifier independently
  confirmed to exist, verbatim, in its source artifact (Section 12);
- **limitation propagation** - every inherited limitation
  independently confirmed present, unweakened, in integrated output;
- **boundary propagation** - every inherited boundary disclosure
  independently confirmed present;
- **read-only guarantees** - checksum comparison of all six input
  artifacts, git HEAD, and task contracts, immediately before and
  after a fresh integration run (mirroring 128F's own checksum
  methodology);
- **fail-closed behavior** - direct probing of each Section 18
  failure condition against hand-crafted invalid/missing inputs, not
  merely re-running 130E's own test suite;
- **no unintended knowledge creation** - independent confirmation that
  every field in a freshly generated integration package traces to
  one of its six source artifacts (Section 4's "entirely derivative"
  requirement, verified rather than assumed);
- **compatibility with every consumed artifact** - independent
  re-confirmation that none of the six input artifacts' own schema,
  generator, or CLI was modified by 130E (`git show --stat` showing no
  file under any of the other five artifact families' own source
  directories, mirroring every prior hardening phase's own
  confirmation method).

**The verification must independently validate fresh artifacts rather
than trusting implementation tests** - 130F generates its own fresh
set of six input artifacts and its own fresh integration package from
them, exactly as 128F generated fresh Historical Memory artifacts
rather than reusing 127E/127F's own scratch output.

## 22. Acceptance Criteria for 130E

Measurable, each independently checkable by 130F:

- **Deterministic output** - two independent fresh generations from
  the same six input artifacts are byte-identical except the two
  approved timestamp fields.
- **Provenance preservation** - 100% of integrated references carry
  all six required provenance elements (Section 11); zero references
  with an incomplete chain reach output (incomplete chains fail
  closed, Section 18).
- **Limitation propagation** - 100% of inherited limitations from
  referenced source content appear, unweakened, in integrated output.
- **Boundary propagation** - every referenced source artifact's own
  boundary disclosure material is present in integrated output.
- **Identifier preservation** - 100% of cited identifiers verified
  present, verbatim, in their source artifact; zero newly-minted
  replacement identifiers; zero merged identities.
- **Executable schema compatibility** - zero modifications to any of
  the six input artifacts' own frozen schema files; the integration
  package itself, if it needs any structured shape beyond what
  `dependency_context_reference` (Section 6) already provides,
  documents that need as a finding for a future, separately governed
  schema-authoring phase, rather than 130E inventing one unilaterally.
- **Read-only guarantees** - checksum-identical repository, git
  history, and all six input artifacts before/after generation.
- **Serialization compatibility** - `serialize_deterministic_json`
  reuse confirmed unchanged; no duplicate serialization logic
  introduced.
- **CLI compatibility** - if 130E introduces a new `pcae repository-
  intelligence` subcommand for integration generation (the expected,
  minimal CLI surface, matching every prior artifact family's own
  `<family> generate` pattern), it accepts only already-established
  option conventions (`--output`, `--pretty`, `--json`, plus explicit
  `--<artifact>` input-path flags for each of the six consumed
  artifacts) - no option that implies reasoning, ranking, or
  execution.
- **Governance compatibility** - `pcae health`/`check`/`doctor task-
  memory`/`push check`/`runtime inspect` all pass identically before
  and after 130E's change; runtime remains `Observed`/`observe`/
  execution-unavailable throughout.

Expected result for every suite: identical pass/fail outcome to the
pre-130E baseline, plus whatever new, additive test coverage 130E's
own bounded implementation introduces for its own new code.

this plan.
